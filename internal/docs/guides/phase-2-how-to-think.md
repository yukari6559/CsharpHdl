# Phase 2 の進め方：考え方と手順（コードなし）

この文書は「仕様は読んだが、何から手を付ければよいか分からない」ときの手順書です。  
API の完成形イメージは [dsl-spec.md](../dsl-spec.md)、生成結果の約束は [verilog-emit-spec.md](../verilog-emit-spec.md)、フェーズ概要は [phase-2-dsl.md](phase-2-dsl.md) を参照してください。

**ここには実装コードは書きません。** 決めること・作る順序・確認の仕方だけを書きます。

---

## 0. いま起きやすい行き詰まり

Phase 1 では「決まった ALU の Verilog 文字列をそのまま書き出す」で十分でした。  
Phase 2 では「利用者がモジュールを記述すると、その内容から Verilog が出る」へ変わります。

行き詰まりの典型は次です。

1. 仕様の完成形（ALU 例）を見て、最初からその書き味を全部実装しようとする  
2. `Signal` が「変数なのか、電線なのか、式なのか」で頭が混ざる  
3. Core（記述 API）と Emit（文字列化）を同時に完成させようとしてどちらも進まない  
4. 動いていた Phase 1 の経路を壊したまま、未完成の DSL だけが残る  

対処の原則は一つです。**一度に一つの問いだけを解く。**

---

## 1. 頭のモデル（これだけ先に固定する）

### 1.1 二段階である

| 段階 | 何が起きるか | 成果物 |
|------|--------------|--------|
| 記述の実行 | 利用者が書いたモジュール定義が動き、回路の構造がメモリ上に残る | モジュール・信号・文のグラフ（いわゆる AST / IR） |
| 生成 | その構造を読んで Verilog テキストにする | `.v` ファイル |

Phase 1 は後段だけを手書きでやっていた状態です。  
Phase 2 は前段を導入し、後段を「手書き文字列」から「構造を読む」に置き換えます。

### 1.2 「計算」ではなく「記録」

DSL のメソッドや演算子は、実行時に ALU の答えを出すためのものではありません。  
「どの信号とどの信号が、どの演算で、どこへつながるか」を **記録** します。

シミュレーションで数値を流すのは別問題です。v0.1 の主目的は Verilog 生成です。

### 1.3 Signal の位置づけ

`Signal` は「名前とビット幅を持つ、回路上の結線ポイント」です。

- ポート（入力・出力）も Signal の一種  
- モジュール内部の中間線やレジスタも Signal  
- wire か reg かは、多くの場合「どう駆動されるか」から後で決まる（最初から厳密に分けなくてもよい）

`Signal` が「整数の箱」だと思うと設計が止まります。  
まずは **識別情報（名前・幅・方向）を持つノード** と考えてください。

## 2. 全体のステップ（この順で進める）

各ステップに「終わる条件」があります。満たすまで次へ行かないでください。

| # | テーマ | 終わる条件 |
|---|--------|------------|
| A | 土台を守る | Phase 1 の「ALU を emit できる経路」が残っている、または意図的に別名で残している |
| B | Signal をデータとして定義する | 名前・幅・方向が取れ、ファクトリでポートを作れる |
| C | Module の骨格 | モジュールを new でき、Describe 相当の入口がある |
| D | 式（Expr） | `A + B` のようなものが「式ノード」として残る（数値結果ではない） |
| E | 文の記録（Comb / Assign / Switch） | Describe 実行後に「何を代入したか」の一覧が取れる |
| F | Emitter | その一覧から Phase 1 と同等の ALU Verilog が出る |
| G | 検証 | スナップショットまたは差分で固定し、幅エラーなど最小チェックを入れる |

`Signal` で止まっているなら、次節の **課題 2** 群から。  
粗マップ A〜G と細かい課題の対応は次節末尾。

## 2.5 現在地 → Phase 2 完了：小さな課題とヒント

ゴールは [phase-2-dsl.md](phase-2-dsl.md) の完了条件 3 つ（DSL の ALU、同期カウンタ、幅不一致エラー）。

各課題は「やること」だけ先に読み、詰まったらヒントを見る想定です。

### 課題 1 — 比較できる足場を残す

**課題 1-a**  
`examples/alu` を、しばらく「今すぐ動く生成器」として使うか、「完成形 DSL の見本」として置くか、自分の言葉で一文決める。

*ヒント:* 見本を examples に置くと、未実装 API でビルドが止まりやすい。完成形の書き味はすでに `dsl-spec.md` にある。比較対象（ゴールデン）が無いと、あとで「DSL 版が正解か」を判定できない。

**課題 1-b**  
CLI から再び ALU の `.v` が出せる状態に戻す（本文を別名ファイルに退避してもよい）。

*ヒント:* いまの CLI は「静的にファイルへ書く」前提の呼び方のままなことが多い。DSL のインスタンスメソッドと取り違えていないか確認する。git の履歴に Phase 1 の生成器が残っている。

**課題 1-c**  
出した `.v` をシミュレータが読めること、内容を後で比較できる形（テストや固定ファイル）に残すことを確認する。

*ヒント:* Phase 2 完了条件の「同等」は、この足場が基準になる。ここを飛ばすと Signal を直してもゴール判定できない。

**課題 1-d**  
ビルドを止めていた「未実装だらけの ideal ALU」を、主経路から外す方針を決める。

*ヒント:* 削除せず `docs` や別パスに「将来の書き味」として残す選択肢もある。重要なのは、日常のビルドが緑に戻ること。

---

### 課題 2 — Signal を「結線ポイント」にする（いまの主戦場）

**課題 2-a**  
ノートに書く: ポート 1 本を Verilog の一行にするために、最低限どんな情報が要るか。

*ヒント:* 名前（識別子）、幅、向き（input/output）。「今の数値」は不要。wire/reg もこの時点では決めなくてよいことが多い。

**課題 2-b**  
仕様の「幅と名前を渡して入力ポートを作る」呼び出しに合わせて、作り方の方針だけ決める（ジェネリックは使う？ 使わない？）。

*ヒント:* v0.1 は非ジェネリックで足りる、と仕様も許容している。工場メソッドがインスタンスの「値を入れる操作」になっていないか見直す。

**課題 2-c**  
幅が 0 以下のときどうするかを一文で決めてから、Signal / In / Out を「持つ・作る・読む」だけ実装する。演算・代入・Comb・文字列生成は禁止。

*ヒント:* 責務を増やすとまた止まる。終わったかの目安は、「この入力の名前と幅は？」にプログラムから答えられること。

**課題 2-d**  
不正な幅を拒否できることを、小さなテストか手動確認で確かめる。

*ヒント:* 後の「幅不一致エラー」（完了条件 3）とは別。まずは「1 本の Signal として成立するか」。

---

### 課題 3 — 空の Module にポートを載せる

**課題 3-a**  
ポート一覧を Module がどう把握するか（自分で登録する／型のメンバーを集める等）を決め、Describe をいつ走らせるかも一文で決める。

*ヒント:* 最初は明示登録の方が動作が追いやすい。Describe は「生成の直前」に呼ぶと、コンストラクタ副作用よりデバッグしやすい。

**課題 3-b**  
論理が空のモジュールをインスタンス化し、「このモジュールのポートは何か」と列挙できるところまで作る。

*ヒント:* ALU の四則はまだ不要。ポート宣言だけ人間が手で Verilog に写せるなら十分。

---

### 課題 4 — 「A 足す B」を式として残す

**課題 4-a**  
次の文の違いを自分の言葉で説明する: 「実行して和を出す」と「和という関係をグラフに残す」。

*ヒント:* DSL がやるのは後者。シミュレーション用の数値実行は別問題。

**課題 4-b**  
ALU に必要な式の種類を最小集合で列挙し、Signal と同じ型に載せるか別型にするかを決める。結果の幅ルールも決める。

*ヒント:* 信号を指すもの、二項演算、定数との比較があれば Switch 付き ALU に届きやすい。別型にすると「結線ポイント」と「関係」が混ざりにくい。幅は仕様の推奨（左辺に合わせる等）をそのまま採用してよい。

**課題 4-c**  
加算ノードを作り、あとから「左・右・演算子」を辿れることを確認する。Verilog はまだ出さない。

*ヒント:* 文字列になっている必要はない。オブジェクトグラフで説明できれば次へ進める。

---

### 課題 5 — Describe の結果をメモリに溜める

**課題 5-a**  
「いま組み合わせ論理のブロックの中にいる」ことを、どう保持するか決める。

*ヒント:* Module がリストを持つ、または記述中だけ有効な文脈オブジェクトを持つ、などが定番。スレッドをまたぐ必要は初期ではない。

**課題 5-b**  
代入と多分岐を、どんな「文」として溜めるかスケッチする。同じ信号へ二回駆動したらいつ怒るかも決める。

*ヒント:* Switch をネストした木のまま持っても、平坦な条件付き代入に落としてもよい。怒りのタイミングは記録時の方が初心者には分かりやすいことが多い。

**課題 5-c**  
Comb・Assign・Switch を足し、ALU 相当の Describe を走らせたあと、「Y は Op に応じて四通り」とデータ構造だけで説明できることを確認する。

*ヒント:* この時点で Emitter を触りたくなるが、先に「記録が正しい」を固めた方が、文字列バグと論理バグを分離できる。

---

### 課題 6 — 記録を Verilog にして ALU を閉じる（完了条件 1）

**課題 6-a**  
組み合わせ論理の出し方を一つに固定する（単純なら条件式の連鎖、複雑なら always 形式、など）。

*ヒント:* [verilog-emit-spec.md](../verilog-emit-spec.md) に両方の例がある。「どちらも適当に」だとスナップショットが安定しない。

**課題 6-b**  
先に「モジュール名・ポート宣言だけ」出る Emitter を作り、Phase 1 ゴールデンのポート部と見比べる。

*ヒント:* body より枠の不一致（幅の書き方、カンマ、方向）で詰まりやすい。枠が合ってから式を足す。

**課題 6-c**  
式 → テキスト、文 → body の順で足し、DSL 経由で ALU 全体を出す。ゴールデン一致または意味同等＋シミュレータ可を確認する。

*ヒント:* 空白や改行まで一致させなくてもよいが、その場合は「何をもって同等とするか」を先に決める。つながったら CLI／テストの主経路を DSL 側に寄せてよい。

---

### 課題 7 — クロック付きカウンタ（完了条件 2）

**課題 7-a**  
Clock / Reset を専用の概念にするか、普通の信号と同じにするか決める。リセットの極性と初期値の渡し方も決める。

*ヒント:* emit 仕様は同期リセット寄り。ALU で使った Comb 用の代入と、クロック縁の代入は意味が違うので、記録上も混ぜない。

**課題 7-b**  
Seq の記録と、posedge の always を出すところまでを、レジスタ 1 本の最小例で通す。

*ヒント:* いきなり多ビットカウンタ全体を書かず、「rst なら 0、否则 next」が 1 本出れば Emitter の骨は折れている。

**課題 7-c**  
`examples` に同期カウンタを追加し、生成物が読める／期待どおり動くことを確認する。

*ヒント:* Phase 2 完了条件の 2 つ目。階層モジュールやメモリは Phase 3 の話なので入れない。

---

### 課題 8 — 幅の失敗を意図的に起こす（完了条件 3）

**課題 8-a**  
幅が合わない組み合わせを、演算・代入・emit のどこで検出するか決める。

*ヒント:* 少なくとも一箇所は必須。早すぎる検出は API がうるさく、遅すぎると原因が追いにくい。代入時がバランス良いことが多い。

**課題 8-b**  
不一致で必ず失敗する経路と、それを固定するテストを用意する。ALU・カウンタの回帰も通す。

*ヒント:* [testing.md](../testing.md) の Phase 1〜2 必須ケースが目安。最後に phase-2 ガイドの完了印と、必要なら integration-log を更新してフェーズを閉じる。

### どの課題から再開するか

| いまの感覚 | 向かう課題 |
|------------|------------|
| emit も例も信じられない | 1-a |
| Signal の中身が決められない | 2-a |
| ポートはあるがモジュールに載らない | 3-a |
| `A + B` の意味が分からない | 4-a |
| Describe しても何も残らない | 5-a |
| 構造はあるが `.v` にならない | 6-a |
| ALU は出たが Seq / カウンタがない | 7-a |

## 3. ステップ A：土台を守る

### やること

- Phase 1 で通っていた「ALU → `.v`」が、開発中も参照できるようにする  
- 理想の DSL 例と、今動く生成経路を混同しない  

### 決めること

- 動く生成経路を残すか、一時的に壊してよいか（推奨は残す）  
- `examples/alu` を「今動くもの」にするか、「将来の書き味の見本」にするか  

### 注意

仕様書の ALU 例は **完成時の契約イメージ** です。  
それを examples に先置きすると、未実装 API だらけになり「何を実装すべきか」が見えなくなります。見本は `dsl-spec.md` に置き、examples は「今の段階で実証できる最小」に寄せると迷いにくいです。

---

## 4. ステップ B：Signal（いま詰まっているところ）

ここが Phase 2 最初の本丸です。**演算も Comb も Emitter もまだ不要**です。

### 4.1 このステップで答える問い

1. 一つの Signal が必ず持つ情報は何か  
2. 入力ポートと出力ポートをどう区別するか  
3. 「幅 32・名前 A の入力」をどう作るか（ファクトリの形）  
4. 利用者が触ってよい操作は何か（この段階では「作る・読む」だけでよい）

### 4.2 推奨する最小情報

少なくとも次は必要です。

| 情報 | 理由 |
|------|------|
| 名前 | Verilog 識別子になる |
| 幅（正の整数） | 仕様の「幅が必須」 |
| 方向（in / out。将来 inout） | ポート宣言に必要 |

内部専用 Signal は、方向なし、または「内部」として後回しで構いません。最初はポートだけで十分です。

### 4.3 仕様との対応で迷いやすい点

| 仕様の書き方 | このステップでの解釈 |
|--------------|----------------------|
| `In.UInt(32, "A")` | 「幅付き入力ポートを作る」工場メソッド。値を入れる操作ではない |
| `In<T>` などのジェネリック | v0.1 では必須ではない。非ジェネリックで始められる |
| wire / reg | Signal 作成時点で決めなくてよい。駆動（Comb/Seq）を入れてからでよい |

### 4.4 このステップでやらないこと

- 加算・論理演算のオーバーロード  
- `Assign`  
- `Comb` / `Seq`  
- Verilog 文字列生成  
- クロック・リセット  

これらを Signal に詰め込むと、また lag します。

### 4.5 終わりの確認（コードを見せなくてもできるチェック）

自分にこう質問できれば B は完了です。

- 「入力 A は幅何ビットで、名前は何か」とプログラムから答えられるか  
- 不正な幅（0 以下など）を拒否する方針があるか  
- モジュール例のポート宣言行を、人間が手で Verilog に書き起こせるほど情報が揃っているか  

まだ「ALU の論理」は不要です。

## 5. ステップ C：Module の骨格

### やること

- 「ハードウェア部品 1 個」を表す型の入口を作る  
- 利用者が論理を書くフック（仕様上の `Describe`）の場所を決める  

### この段階で決めること

- ポート一覧を Module がどう把握するか  
  - 例: プロパティを反射で集める / 登録メソッドで明示登録する  
- Describe をいつ呼ぶか（new 時 / emit 時）  

### 終わりの条件

- 空に近いモジュールをインスタンス化できる  
- 次のステップで「文を溜める場所」を Module 側に足せる見通しがある  

---

## 6. ステップ D：式（Expr）— Signal の次にやること

Signal が「結線ポイント」なら、式は「結線ポイント同士の関係」です。

### 頭の切り替え

- `A + B` → 数値の和、ではない  
- `A + B` → 「左が A、右が B、演算が加算」というノード  

### このステップで決めること

- 式の種類の最小集合（ALU に必要なものだけ）  
  - 信号参照  
  - 二項演算（加減・論理）  
  - 定数との比較（Switch 用）  
- 演算の結果の幅ルール（仕様推奨: 左辺幅に合わせる、など）  
- 演算子を Signal に載せるか、別の式型に載せるか  

### 終わりの条件

- 「A と B の加算」をオブジェクトとして保持し、後から辿れる  

---

## 7. ステップ E：文の記録（Comb / Assign / Switch）

### やること

Describe の実行中に出た代入や分岐を、Module（またはビルダー）に蓄積する。

### 決めること

- 「いま Comb の中にいる」状態をどう持つか  
- 同一信号への二重駆動をいつ検出するか（記録時 / emit 時）  
- Switch を木構造で持つか、平坦な条件付き代入に落とすか  

### 終わりの条件

- ALU 相当の Describe を走らせたあと、「Y は Op に応じて四通り」とデータ上で説明できる  
- まだ Verilog 文字列は無くてよい  

---

## 8. ステップ F：Emitter

### やること

蓄積した構造を [verilog-emit-spec.md](../verilog-emit-spec.md) に沿って文字列化する。

### 進め方

- 最初のターゲットは Phase 1 と同じ ALU のみ  
- Comb が単純なら連続三項演算子、複雑なら always 形式、のどちらにするかを一度決めて固定する  
- Seq / メモリ / 階層は後回し  

### 終わりの条件

- DSL 経由の出力が、Phase 1 のゴールデンと意味的に同等（または文字一致）  

---

## 9. Signal で迷ったときの判断ツリー

```
Q1. いま欲しいのは「ポートを作って名前と幅を保持」か？
    YES → ステップ B だけやる。演算は禁止。
    NO  → Q2 へ

Q2. 「A + B を表したい」か？
    YES → ステップ B が終わってから D。Signal 単体の問題ではない。
    NO  → Q3 へ

Q3. 「Y に代入したい」か？
    YES → ステップ E。Assign は文の記録。Signal の中に Verilog を書かない。
    NO  → Q4 へ

Q4. 「.v を出したい」か？
    YES → ステップ F。先に E までデータが溜まっていること。
```

「Signal の実装が分からない」と感じるとき、実際は Q2〜Q4 を同時に解こうとしていることが多いです。  
その場合は Q1 に戻ってください。

## 10. 設計で先に人間が決めるべきこと（大きい変更）

次は仕様の解釈が分かれるので、エージェントに一括実装させるより、短くメモしてから実装した方が安全です。

| 決定項目 | 選べる方向の例 | 初期のおすすめ |
|----------|----------------|----------------|
| ポート収集 | 反射 / 明示登録 | 最初は明示登録の方が分かりやすい。慣れれば反射でも可 |
| 式の置き場 | Signal に演算子 / 別型 Expr | 別型にすると責務が分離しやすい |
| wire/reg | 宣言時指定 / 駆動から推論 | 駆動から推論でよい |
| ジェネリック幅 | `In<T>` / `UInt(n)` のみ | `UInt(n)` のみで開始 |
| Describe の呼び出し | コンストラクタ / Emit 前 | Emit 前の明示呼び出しが追いやすい |

決めた内容は、このファイルの末尾「決定ログ」か [integration-log.md](../integration-log.md) に一行で残すと、後から迷いません。

## 11. レビューを頼むときの使い方

このリポジトリでは実装主体は人間です。レビューを依頼するときは、次を添えると具体的な改善点を返しやすいです。

- 今どのステップ（A〜G）にいるか  
- そのステップの「終わる条件」を自分は満たしたと思うか  
- 迷っている決定項目（上記表のどれか）  
- 大規模修正が必要そうか（必要なら指摘のみ求め、実装は自分で行う）  

レビュー側の約束（このプロジェクト向け）:

- 具体的な改善点を出す  
- 大規模修正が必要なときは、方針と分割案を示し、実装は依頼者（人間）に任せる  
- 要望がなければ具体コードは出さない
